# MocknSlice architecture

## Current upgrade architecture

The Studio shell and retained legacy workflow share serializable project state. Native folding/custom definitions and papercraft compile panel graphs into physical boundaries; sliced/panel generators retain their mode-specific pure kernels. A frozen `PreparedOutputProvider` snapshot joins 2D/3D inspection, readiness and SVG/PDF. Verified currentness, topology, placement and operation checks gate production; old outputs remain accessible as drafts.

Papercraft uses typed workers for preparation/optimization, an immutable accepted working mesh for stable edits, and a confirmed source-update proposal. Relinking retains ambiguous intent as persistent unresolved records. Worker cancellation and project/source identity checks protect last valid artifacts; autosave guards prevent late hydration/save completions from overwriting newer intent. Renderer-only triangulation and GPU objects stay outside serialized graphs. Version-locked authoring definitions are bounded data, not executable code.

Project/schema storage is v9. IndexedDB database version 2 adds the immutable template library without replacing projects, settings or autosave pointers. The registry exposes seven working folding families and five working construction recipes, with no unsupported FEFCO entries. ADRs 0026–0035 record the staged transition; [UPGRADE_HANDOFF.md](UPGRADE_HANDOFF.md) maps implemented goals to remaining release work. Legacy-specific descriptions below remain useful compatibility history where they differ from these current native paths.

## Layer boundaries

### Domain

`src/domain/` contains serializable TypeScript types for projects, models, materials, per-mode settings, fabrication parts, sheet layouts, operations, exports, validation, projected profiles, fold panels, fold edges, tabs, mesh-unfold faces, seams, hinges, islands, overlaps, panel features, and assembled-preview data. The domain imports neither React nor Three.js. Fabrication dimensions have `Mm` names or use the `Millimetres` alias.

### Geometry engine

`src/geometry/` exposes pure functions for mesh normalization, topology validation, model transforms, plane placement, triangle-plane intersection, endpoint welding, contour tracing, outer/hole classification, stacked and orthogonal waffle generation, slot construction, convex profile fitting, folding-template generation, part transforms, deterministic row layout, tight Standard output layout, sheet validation, and fabrication-output preparation. Functions run in unit tests without a browser. Expensive orchestration uses typed messages under `src/workers/` while calling the same pure functions; inexpensive sheet arrangement and output preparation remain synchronous.

Phase 6 shape fitting implements deterministic axis projection, convex hull, convex offset, visible enclosure-preserving simplification, optional outward envelope resizing, and fixed-topology template generators. Custom width, length, and height are mapped through the fitting axis, may enlarge but never undercut the fitted envelope, and never mutate the source mesh. These functions return serializable source/fitted profiles, resolved dimensions, panels, fold edges, tabs, fabrication parts, assembled panel data, and structured issues. The worker orchestrates fitting and generation with cancellation, input hashes, and stale-result rejection.

Phase 8 topology and unfolding remain pure geometry. The engine builds indexed triangle adjacency, rejects unsupported topology, derives a deterministic acyclic hinge forest, flattens rigid triangles, scores face overlaps, adds paired seams and tabs, and returns a stable hash. The fold-preview helper derives animated vertices without mutating the stored result.

Panel construction is another pure generator. It converts inside dimensions, base/wall, divider, and lid stock thicknesses, a material kerf snapshot, a default joint family, stable paired connection overrides, bounded front/back profiles, target pitch, clearance, lid choice, optional width/depth divider families, and stable-ID panel features into serializable panel outlines, slot and feature holes, paired joints, labels, exact assembled outlines/holes, issues, and an input hash. Every base/wall connection is resolved once from a stable pair key before both edge treatments are emitted, preventing conflicting edge specifications. Arch, gable, and stepped profiles replace only the open top segment while retaining the nominal side-joint endpoints; generated outlines are transformed directly into assembled vertices. Divider positions account for divider stock so every cell has equal clear space. Divider side joints are explicit face-receiver joints rather than pretending that an interior wall slot is a boundary edge. Simultaneous families add explicit half-lap crossing joints and complementary half-height outline notches. Feature geometry is resolved only after the exact jointed panel exists; cutout and label footprints share deterministic containment, boundary-distance, and overlap predicates. Circles use a fixed 48-segment polygon. Every generated part carries its effective role-specific thickness, and the presentation layer uses it for 3D extrusion without adding Three.js objects to project data.

STL parsing/normalization, stacked-slice generation, two-family waffle generation, folding-template generation, low-poly mesh unfolding, and panel construction run as cancellable Web Worker requests. The worker returns plain serializable geometry and validation data; it does not return Three.js objects.

### Application state

`src/state/` composes separate Zustand slices for project lifecycle, model import and inspection, fabrication settings, sheet layout, viewport/workflow state, selection, material library, history, export settings, and validation. Persistent state contains plain data only; completed wizard steps remain transient and are inferred from hydrated project artifacts. Each fabrication mode has a typed patch action, and panel construction also has atomic replacement, recipe-application, and feature add/update/duplicate/remove actions. A recipe application resolves one complete panel settings value and records one undo entry without touching inactive modes. Each feature action likewise creates one history entry. Inactive settings are preserved, while output becomes stale only when the active canonical input changes. The Simple/Advanced preference is browser-local and is not part of `ProjectData` or any generation signature. Visible workflow steps are derived from fabrication mode, experience mode, generation state, and blocking errors. Imported mesh positions and indices are plain arrays. Project-changing actions record undo history and mark autosave pending; camera, workflow navigation, active-sheet selection, experience mode, and viewport changes do not enter history. A pointer drag previews locally and commits one placement or feature change when released.

### Presentation

`src/app/`, `src/components/`, and `src/viewports/` implement the shell and views. A step registry mounts only the active workflow panel while the preview remains persistent. Panel construction omits a separate source/preset step: a compact bilingual preset menu calls the same state and geometry pipeline from Configure. Its stock and divider counts use keyboard-accessible range controls with numeric output, dynamic physical maxima, and a live clear-cell measurement. The focused feature composer uses native SVG for panel-local editing, pointer capture for local drag previews, Shift-constrained movement, live opening dimensions, keyboard movement with fixed millimetre modifiers, touch-sized targets, and numeric fallbacks. RTL changes layout and text direction but never mirrors local geometry coordinates. Three.js buffer and extruded part geometry is recreated and disposed inside the 3D presentation boundary from serializable mesh and contour data. Selected assembly edges project an HTML treatment editor at their 3D midpoint; serializable settings remain in Zustand, while treatment badges and tab markers are recreated as presentation-only objects. A compact native selector provides equivalent keyboard edge selection. Setting changes mark an existing result stale and regeneration is an explicit user action, with an additional reminder after opening or label edits. The 2D preview renders the same paths as a whole-sheet SVG whose document box scales during zoom. Selection is synchronized through stable feature, edge, part, and panel IDs and retained across regeneration. Stable Zustand selector results prevent external-store render loops, and a resettable viewport error boundary prevents a rendering failure from removing project and inspection controls.

### Persistence and file exchange

`src/persistence/` defines a repository interface and IndexedDB implementation. `src/exporters/` owns versioned project serialization, validation, and migration entry points. The browser stores named project data and the last autosave pointer in separate object stores.

Prepared parts are derived at export/preview time from generated parts plus serializable output settings. Kerf offsets and fold-line conversion never replace generated source geometry. In Simple mode, the 2D viewport and exporters receive an explicit ephemeral tight layout; in Advanced mode they receive persisted `sheetLayouts`. Exporters never rewrite or clone the project to select an effective layout. PDF objects and content streams are emitted directly as deterministic vector data; no canvas capture or raster content is used.

MocknSlice project version 8 extends the complete `ModeSettingsByMode` data with stable connection overrides and boundary glue tabs for panel construction and folding. Import follows parse, envelope validation, version dispatch, legacy validation, explicit v1–v7 migration, strict v8 settings validation, then runtime preparation. SliceFold versions 1–5 and MocknSlice versions 6–7 remain import-compatible. IndexedDB stores `storageVersion: 8` beside the project while retaining `metadata.id` as its key path; unversioned records containing `modeParameters` use the same v6 migration path and raw v7 records use the file upgrader.

Every generation request is built from a pure canonical input and recorded with signature version 2. The input hash is captured before worker dispatch and rebuilt before accepting a result. Standalone folding has no model dependency, panel construction uses stable panel provenance rather than model provenance, seam keys, features, connection overrides, and boundary tabs are normalized by stable ID, and non-finite or undefined values fail before dispatch. Folding hashes only records for the active template. Selection remains runtime-only and cannot stale output.

Connection editing uses an acyclic crease graph and deterministic rigid 2D edge alignment. Panel creases remove internal cuts and produce one closed fabrication contour per connected component; folding cuts split components and seam-to-crease edits rebuild their flat alignment. Glue tabs replace a straight eligible boundary segment with a shouldered outline and add a score at the base. Structural or geometric conflicts remain in settings and block regeneration without replacing the previous valid artifact.

Current panel settings permit butt and complementary finger boundary joints. The retired tab-slot discriminator remains accepted only at legacy import/result boundaries. Runtime preparation converts it to finger joints, emits `PANEL_TAB_SLOT_REPLACED`, and leaves old generated artifacts inspectable but stale; direct legacy geometry calls receive `PANEL_JOINT_UNSUPPORTED` rather than unreliable through-slot output.

## Data flow

User input updates a focused Zustand action. Meaningful project actions record a previous project snapshot, update the serializable project, and schedule repository autosave. Active canonical input changes preserve generated geometry but mark it stale; irrelevant material fields and inactive settings do not. Stacked, waffle, template, mesh-unfold, and panel construction generation create a deterministic initial layout from the first sheet's settings. Presentation selectors reconstruct transformed geometry from persisted placements, assembled panels, or unfolded triangle hinges. Project JSON export serializes the same project data; import validates and replaces it through history. Fabrication SVG exports the active sheet and PDF exports all used sheets using those same numeric transforms and prepared paths.

## Dependency rules

The template registry (`src/templates/`, ADR 0027) separates bilingual definitions, bounded parameters, version-locked resolved instances and local generator functions. Existing selectors read only lightweight definitions; worker folding dispatch uses registered legacy functions. The unchanged open-box builder lives in `src/templates/families/openBoxNet.ts` and shared folding helpers remain pure. Registry graph generation wraps legacy geometry during transition and cannot confer closed-contour or physical certification.

The MocknSlice 2.0 design graph is introduced alongside existing result types (ADR 0026). `src/domain/designGraph.ts` defines named panel vertices, physical connections, manufacturing features and pieces. `src/geometry/designGraph/` validates identity, finite geometry, contour topology, stock, connection lengths, hinge forests, ownership and duplicate cuts. The two covered folding adapters and butt-enclosure adapter project unchanged parts and rigid assembled poses; they remain disabled in public dispatch. Slicing and legacy unfolding retain their existing contracts.

Manufacturing features hold one authoritative point array plus original path/label metadata. Piece feature ordering retains exact legacy SVG/PDF bytes. Assembled panels derive from that panel's flat boundary and a serializable rigid pose; an explicit vertex-reference ordering preserves legacy assembled inventory without storing another shape. The adapter recovers correspondence using physical hinge targets because legacy 2D and 3D vertex orders differ. Explicit closing vertices in old panel paths are retained in exports and normalized only for topology predicates. Legacy graph manufacturing remains unverified; this phase does not grant production readiness or migrate persistence.

- Domain code may not import React, browser APIs, Zustand, or Three.js.
- Geometry may import domain types but not state or presentation code.
- Persistence works through `ProjectRepository` so a future storage adapter does not affect UI code.
- Optional polygon or solid geometry libraries require a browser spike and ADR before adoption.

The initial panel-feature predicates remain small in-house pure functions. The `@flatten-js/core` spike was rejected in ADR 0022 after adding roughly 107 KB raw / 24 KB gzip to both representative main and worker bundles for the required minimal operations. No external geometry objects cross domain, worker, state, preview, or export boundaries.
